# Native builds

## Generated native projects

- `ios/` and `android/` are generated by `npx expo prebuild` from `app.json` (or `app.config.ts`) and the config plugins it lists, and are git-ignored. A native change (a permission, an entitlement, an Info.plist key, a Gradle setting) goes in the config or in a config plugin in `plugins/`, never in the generated folders, which the next prebuild overwrites.
- A change to the config or a plugin reaches a build through `npx expo prebuild --clean`; `expo run:ios` alone reuses the folders already generated.
- A config plugin that edits a file another plugin also edits states its place in the plugin list and why. Mods registered later run first on the same file, so a plugin meant to remove what another adds goes before it in the list.

## Dependencies

- Expo packages are added with `npx expo install`, which picks the version that matches the SDK. After adding or upgrading any package, `npx expo install --check` reports the ones that do not match; a mismatch can build and then fail at runtime, in the native module that does not match.
- Upgrading `expo` upgrades every app in the monorepo that depends on it together, so one version of each native module is installed.

## Checking the output

Metro's module resolution and asset inlining fail without an error: a missing file extension in `resolver.sourceExts` or a Babel plugin that did not run leaves the module empty. After a change to `metro.config.js`, `babel.config.js` or the files they handle, export the bundle and look for a string that is there only when the pipeline worked (a table name from a bundled migration, a value from env).
