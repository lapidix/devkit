# i18n

## Engine

The project picks one engine (i18next, a typed dictionary of its own, …) and uses only that one. Whatever the engine, translation keys are typed: a key that does not exist fails type-checking.

## Keys

`{area}.{purpose}.{name}`:

```
user.validation.bioMax
user.errors.emailTaken
user.actions.invite
common.errors.network
```

- **area**: the domain, with the same name as its entities, features and pages folders (`user`). A screen with no domain takes its page folder's name (`home`, `dashboard`). Text that belongs nowhere else goes under `common`.
- **purpose**: the kind of text (`validation`, `errors`, `labels`, `actions`, `status`, …). The project defines the list.
- **name**: camelCase.

The area comes first so one domain's text sits together and matches its folders.

## Rules

- Every piece of text a user sees goes through `t()`. The project lists what is never translated, such as product names and terms like CPU or GPU.
- Language parity is a test, not a report: every language has the same key set, no empty text, and the same interpolation slots (`{count}`). Typed keys alone miss part of this; i18next derives its types from one language's file and never checks the others.
- Module-level constants hold keys, not translated text, and the component translates them when it renders. A constant is built once, when the module first runs, and never follows a language switch.
- Never build a sentence from pieces (`t('a') + name + t('b')`); word order differs between languages. One sentence is one key with interpolation.
- Never pass inline fallback text (`t('organization.errors.seatLimitExceeded', 'No seats left')`). A missing translation then shows the fallback and nobody notices. Typed keys make it unnecessary.
- Validation messages, `meta.successMessage` and error text are keys; the screen translates them when it renders (`rules/frontend/entities.md`, `rules/frontend/react-query.md`).

## Keys passed as data

A key written straight into `t('…')` is type-checked. A key passed along as a plain string is not: a schema message, a `setError` message, `meta.successMessage`, the default failure text. Those keys come from a constant checked against the key type:

```ts
// entities/user/constants/user.message.const.ts
export const USER_MESSAGES = {
  bioMax: 'user.validation.bioMax',
  emailTaken: 'user.errors.emailTaken',
  created: 'user.toast.created',
} as const satisfies Record<string, TranslationKey>;

z.string().max(USER_BIO_MAX_LENGTH, USER_MESSAGES.bioMax)
```

- A domain's keys live in `entities/{d}/constants/{d}.message.const.ts` as `{D}_MESSAGES`, exported through the slice's `index.ts`. Keys that belong to no domain live in `shared/constants/common.message.const.ts` as `COMMON_MESSAGES`.
- The object is flat, with camelCase names.
- `TranslationKey` is the engine's key type, exported from `shared/libs/i18n` (a typed dictionary uses `keyof typeof ko`).
- Keys written straight into `t('…')` in a component stay literal.

A zod check given no message returns zod's own English text, which is not a key. zod's global error map gives every such check one generic key, so English never reaches the screen; a check whose message matters passes its own key, which wins:

```ts
// shared/libs/i18n/zod.error-map.ts, run once at startup
z.config({ customError: () => COMMON_MESSAGES.invalid }); // zod 3: z.setErrorMap(() => ({ message: COMMON_MESSAGES.invalid }))
```

The map returns a key and translates nothing; translation stays in the UI.

## If you use i18next

- One namespace per area: the domains and `common`.
- Types come from the source language's files through `CustomTypeOptions`; the parity test covers the other languages.
